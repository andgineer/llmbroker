# Использование

Синхронный скрипт — самый простой сценарий. Для FastAPI и воркеров см.
[Асинхронность](async.md).

## Пул моделей

Пул — это курируемый список бесплатных LLM, и вы получаете его, попросив брокер:

```python
llms = llmbroker.Broker()
```

Ничего создавать и ничего поддерживать не нужно. Сформируйте заготовку ключей и
заполните те, которые легко достать:

```bash
llmbroker env freetier > .env
```

`llmbroker env` печатает подсказку над каждым ключом — где его получить. Модель
без ключа просто остаётся неактивной, это не ошибка. Брокер читает `.env` из
рабочего каталога; переменная окружения важнее его.

Провайдера, не терпящего параллельных запросов с одним ключом, ограничивает
`parallel` в его записи. Для пула это решает курируемый список, а не вы — файл
принадлежит llmbroker, см. [ниже](#file); для своей модели это поле `LLMConfig`,
который вы объявляете сами.

### Свои платные модели {#direct}

Ничто из объявленного здесь в пул не попадает: пул продаёт failover между
взаимозаменяемыми бесплатными endpoint'ами, и вашему корпоративному шлюзу нечего
делать под чужим 429 — если вы сами не поместили его туда [осознанно](#file).
Объявленные модели вызываются по имени:

```python
llms = llmbroker.Broker(direct=["opus"])
llms.direct("opus").ask("...")
```

`"opus"` — алиас из курируемого каталога платных моделей, вечная ручка, которую
llmbroker держит наведённой на текущее поколение. Передайте вместо алиаса
`LLMConfig`, чтобы объявить свой endpoint ровно так, как написано. В обоих случаях
ничего не сохраняется: объявление в коде — единственный источник истины. См.
[Прямые вызовы моделей](direct.md).

### Где живёт список {#file}

Класть его никуда не нужно. Брокер держит список в собственном каталоге
llmbroker — `~/.cache/llmbroker` на Linux, `~/Library/Caches/llmbroker` на macOS
— и там же его обновляет. Каталог переносится переменной `LLMBROKER_HOME`: это
то, что нужно контейнеру без доступа к кэшу.

Этот файл пишет llmbroker, а не вы: обновление перегенерирует его целиком, и в
нём лежит только пул — модель, которую вы зовёте по имени,
[объявляется в коде](direct.md). Указать брокеру свой файл со списком нельзя —
список приходит именем курируемого пресета и никак иначе. Назвать можно базу:

```python
llms = llmbroker.Broker("postgresql://…")   # реестр, ключи и журнал — всё сразу
```

См. [Серверы и кластеры](server.md). Чтобы задать пул самому, передайте объект,
реализующий протокол реестра, и скажите, чему он следует:

```python
llms = llmbroker.Broker(registry=MyRegistry(), sync=None)        # только ваши записи
llms = llmbroker.Broker(registry=MyRegistry(), sync="freetier")  # ваши плюс наши
```

| что передали | `sync=` не указан | записи, которые вы внесли сами |
|---|---|---|
| ничего или URL базы | следует `"freetier"` | обновление их не трогает |
| объект реестра | ошибка — скажите, чему | обновление их не трогает |

Обновление переписывает только то, что записала синхронизация, — так что
«курируемый бесплатный пул плюс пара своих endpoint'ов, в одной маршрутизации» —
это просто реестр, где лежит и то и другое.

#### Своя запись — в пуле {#own-entry}

Свою запись кладут через протокол реестра, а не записью строк: раскладка таблиц
принадлежит llmbroker и может меняться от релиза к релизу. Прочитайте, что там
есть, добавьте своё и запишите всё обратно — `mirror` зеркалит целиком, так что
всё не переданное удаляется:

```python
from llmbroker.models import LLMConfig
from llmbroker.postgres import Registry

registry = Registry(pool)
mine = LLMConfig(
    name="my-gateway",
    base_url="https://gw.internal/v1",
    model="m",
    api_key_ref="MY_GATEWAY_KEY",
)
await registry.mirror([*await registry.load(), mine])
```

Ничто не помечает её как нашу, поэтому никакая синхронизация её не удалит и не
перепишет. Это участник пула, и роутер делает на неё failover; endpoint, который
вы хотите вызывать по имени, — это [объявленная модель](direct.md), и она нигде
не хранится.

### Какая модель пробуется первой {#weight}

Это решает не порядок строк, а `weight`:

```toml
[[llms]]
name        = "google-gemini-3.5-flash-lite"
base_url    = "https://generativelanguage.googleapis.com/v1beta/openai"
model       = "gemini-3.5-flash-lite"
api_key_ref = "GEMINI_API_KEY"
weight      = 0.75
```

Вес — число от 0 до 1: насколько хороших ответов вы ждёте от этой модели, по той
же шкале, что и записываемые вами оценки. Больше — раньше в очереди. По
умолчанию `0.0`, поэтому запись, добавленная без веса, пробуется после всех
взвешенных: проставьте вес своим записям, если хотите, чтобы они соревновались
на равных.

Это отправная точка, а не жёсткий порядок. Каждая оценка, записанная через
[`record_quality()`](#quality), сдвигает модель с её веса к тому, что она
зарабатывает на деле, а когда оценок накопится достаточно, вес перестаёт
учитываться совсем: порядок определяют только оценки, как бы вы ни расставили
модели вначале. Модель, которую ещё никто не оценивал, стартует там, куда её
поставили, а не со дна, откуда ей было бы не выбраться.

!!! tip "Ключи не обязаны лежать в `.env`"
    AWS Secrets Manager, Vault, БД или своё хранилище — см. [API-ключи](secrets.md).

### Держать пул свежим {#sync}

Провайдеры приходят и уходят, курируемый пресет за ними следует. Делать для этого
ничего не нужно. Когда обновление хочется форсировать — это один вызов, и он
возвращает отчёт о сделанном:

```python
report = llms.sync("freetier")           # имя пресета — единственный вызов в сеть
print(llmbroker.format_report(report))   # или отправьте отчёт в свой админский канал
```

Но обычно это не нужно. **Курируемый список поддерживает себя сам** — без
аргумента и без задачи в расписании: провайдеры закрывают бесплатные endpoint'ы
без предупреждения, поэтому список, который перестал обновляться, постепенно
перестаёт работать. Брокер перепроверяет его примерно раз в сутки, лениво — на
вызове, который вы и так делали, никогда по таймеру, так что простаивающий
процесс не делает ничего.

Обновление best-effort: если каталог недоступен, брокер напишет предупреждение в
лог и продолжит на том конфиге, который уже есть. Явный вызов `llms.sync(...)`
наоборот бросает исключение — вы его запросили, вам и обрабатывать.

**Проверка, которая ничего не изменила, ничего и не трогает.** Список
переписывается, только если курируемый действительно сдвинулся, — проверка, не
нашедшая новостей, оставляет его побайтово тем же, вместе с mtime.

Чтобы не следовать ничему — потому что реестр вы наполняете сами — скажите об
этом; интервал проверки тоже ваш:

```python
llmbroker.Broker(sync=None)              # ничего не обновляется
llmbroker.Broker(sync_interval=3600)     # проверять раз в час
```

### Где llmbroker хранит своё состояние

llmbroker хранит немного своего: скачанный пресет, платный каталог, время
последней проверки обновлений — а если базу вы не назвали, то ещё и сам
список моделей, на котором он работает, и журнал вызовов. Всё это лежит в одном
каталоге на машине — `~/Library/Caches/llmbroker` на macOS,
`$XDG_CACHE_HOME/llmbroker` на Linux, `%LOCALAPPDATA%\llmbroker` на Windows.
Перенести его можно через `$LLMBROKER_HOME` или для отдельного брокера через
`home=` — так два проекта на одной машине держат полностью раздельное состояние.

Ничто там не является источником истины: удалите каталог или запуститесь там, где
писать некуда (read-only контейнер), — брокер продолжит работать. Он скачает
заново, а в read-only случае просто ничего не запомнит между запусками. Даже
совсем без сети первый запуск стартует с копии пресета, вшитой в пакет.

Один журнал на машину в режиме без базы — это сознательно: ключи там берутся из
окружения, значит лимиты, которые он помнит, действительно относятся к одному
пулу, а журнал, размазанный по рабочим каталогам, заставлял бы каждый запуск
заново нарываться на тот же 429. Нужен отдельный журнал проекту — передайте
`home=`.

Чтобы поддерживать реестр в базе свежим из собственной задачи деплоя, см.
[Серверы и кластеры](server.md).

В отчёте стоит понимать четыре вещи:

- **Ожидающий ключ (pending key)** — модель ждёт ключ, который вы не задали. Это
  безобидно: она остаётся неактивной, а пул работает на остальных. В отчёте
  написано, где взять ключ.
- **Оставленная запись (kept)** — модель, чей провайдер ушёл из курируемого
  списка, пока у вас ещё есть ключ к нему. С ней ничего не происходит: она
  маршрутизируется ровно как раньше и исчезнет сама, когда перестанет работать.

  ```
  kept: openrouter-nemotron — the lineup no longer carries OPENROUTER_API_KEY
  and this installation has a key for it, so it stays
  ```
- **Списанная запись (retired)** — та же модель после того, как ваш собственный
  журнал вызовов доказал, что она мертва: хотя бы один 401/403/404 и ни одного
  успеха. Неделя из 429 и 5xx не доказывает ничего и ничего не меняет. Удаление
  записи из вашего конфига — единственное разрушительное действие синхронизации,
  поэтому строка показывает доказательство:

  ```
  retired: groq-llama-3.3-70b — 401 since 2026-07-02, no successful call since;
  the lineup dropped it too
  ```
- **Неиспользуемый ключ (unused key)** — ключ, который у вас реально есть и на
  который в вашем конфиге больше никто не ссылается. Отзывать ли его у
  провайдера — ваше решение, а ваша собственная запись, которая его ещё использует,
  убирает этот совет вовсе. Провайдер, ключа к которому у вас никогда не было,
  просто тихо исчезает — отзывать нечего.

Всё правило в одном: синхронизация никогда не отбирает модель, которую вы можете
вызвать, — разве что её заменяет тот же провайдер или ваш журнал говорит, что она
не работает.

### Наблюдение за пулом {#pool-health}

Один вызов отвечает на вопрос «здоров ли пул?» — факты по моделям и картина по
пулу целиком приходят с одного объекта:

```python
snap = llms.snapshot()

print(f"{snap.providers_usable} of {snap.providers_total} providers usable")
if snap.degraded:
    print("остался один лимит — переключаться некуда")

for key in snap.missing_keys:
    print(f"{key.api_key_ref} держит {', '.join(key.entry_names)}")
    print(key.help)                      # где его взять

for key in snap.direct_missing_keys:     # ваши собственные модели, вызываемые по имени
    print(f"{key.api_key_ref} — direct({key.entry_names[0]!r}) не сработает")
    print(key.help)

for name, llm in snap.items():           # по-прежнему отображение имя -> факты о модели
    print(name, llm.has_key, llm.cooldown_until)
```

`direct_missing_keys` намеренно отделён от `missing_keys`: объявленная вами модель
никогда не маршрутизируется, поэтому отсутствующий у неё ключ не может ухудшить
пул, а появившийся в пуле провайдер — не может её починить. `help` у обоих один и
тот же: из вашего блока `[keys]`, если вы его написали, иначе из курируемого
каталога.

Единица счёта — провайдер, а не модель: две записи на одном API-ключе — это один
лимит, и считаются они один раз. Пул с одним работающим провайдером —
**degraded**: отвечать он ещё может, но при rate limit переливаться некуда.
Отзовите или смените ключ — счётчик догонит на ближайшем reconcile, так что числа
не отстают от ваших ключей. Модели, выключенные вами вручную, продолжают считать
своего провайдера: этот вердикт виден в строках моделей выше.

Тот же вердикт llmbroker пишет в лог, так что на него можно повесить алерт без
опроса. Обе строки — `ERROR`, и вы получаете по одной на каждую смену состояния,
включая падение с первой во вторую:

```
pool degraded, no failover left: 1 of 3 providers usable — no key for GEMINI_API_KEY, GROQ_API_KEY
pool cannot serve any request: no provider has a key — no key for ...
```

Восстановление пишет один `INFO` (`pool recovered: 3 of 3 providers usable`);
появление следующего провайдера после этого отдельной строки не стоит. Сами по
себе недостающие ключи никогда не алерт — двух провайдеров может быть ровно
столько, сколько вам нужно.

## Вызов брокера {#calling}

```python
llms = llmbroker.Broker()

reply = llms.ask("Переведи на английский: Привет мир")
print(reply.text)

# Полный messages API
reply = llms.chat([
    {"role": "system", "content": "Отвечай кратко."},
    {"role": "user",   "content": "Что такое Python?"},
])
```

Ограничить время всего вызова:

```python
try:
    reply = llms.ask("Вопрос", wait=5.0)   # максимум 5 секунд от начала до конца
except llmbroker.NoLLMAvailableError:
    print("Никто не ответил за отведённое время")
```

`wait` покрывает обе половины вызова: ожидание свободной модели *и* сам ответ.
Провайдера, который к концу бюджета всё ещё думает, брокер бросает — и не
наказывает за это, потому что дедлайн был ваш, а не его вина. Без `wait` одна
попытка ограничена только внутренним потолком в 60 секунд.

При этом модель, не уложившаяся в ваш бюджет, перестаёт быть первым выбором для
столь же коротких бюджетов — следующий вызывающий получит соседа, а не ту же
ловушку: за находку платит один вызов, а не все. Ничего не отключается:
вызывающие с более щедрым бюджетом по-прежнему идут к этой модели первыми, она
используется, когда других не осталось, а первый её удачный ответ метку снимает.

`wait=0` — единственное исключение: это «не вставать в очередь», а не «ответить
мгновенно»: пробуются все модели, свободные прямо сейчас, но своего дедлайна на
ответ вы не задаёте. Закрывать брокер в скриптах не нужно; когда всё же нужно —
см. [Серверы и кластеры](server.md#closing).

Чтобы печатать ответ по мере написания, а не целиком, пул умеет стримить —
`async for delta in llms.stream(...)`, только async, см.
[Асинхронность](async.md).

## Оценка качества {#quality}

Оценивайте ответы — брокер выучит, какие модели хороши для каких задач:

```python
reply = llms.ask("Кратко перескажи этот пункт договора", operation="summarize")
reply.record_quality(0.9)   # 1.0 — хороший ответ, 0.0 — неудачный; вне [0, 1] — ValueError
```

Оценки копятся по паре `(модель, операция)`: модель, стабильно слабая на данной
операции, уходит в конец очереди, а накапливаясь, они вытесняют [вес](#weight),
с которого она начинала. Демоция мягкая — если других моделей нет, она
всё равно ответит — и снимается новыми хорошими оценками; отдельного «сброса»
нет. Вызовы без `operation=` попадают в один общий bucket.

**Оценить позже.** Вердикт часто приходит спустя долгое время после вызова —
пользователь просматривает созданный LLM артефакт через день. Сохраните
`reply.llm_name` и переданную операцию во время вызова, а оценку запишите, когда
она появится:

```python
# во время вызова сохраняем нужное
llm_name, operation = reply.llm_name, reply.operation

# ...через день, когда приходит отзыв пользователя
llms.record_quality(llm_name, operation, 0.0)
```

Это попадает в тот же bucket `(модель, операция)`, что и `reply.record_quality`;
исходный вызов может уже не существовать — оценка самодостаточна.

Пороги и размер окна оценок настраиваются — см.
[`Optimizer`](reference.md#llmbroker.Optimizer).
