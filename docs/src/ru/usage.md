# Использование

Синхронный скрипт — самый простой сценарий. Для FastAPI и воркеров см.
[Асинхронность](async.md).

## Пул моделей

Возьмите готовый пул бесплатных LLM и сформируйте `.env` с ключами:

```bash
llmbroker preset freetier > llms.toml
llmbroker env llms.toml > .env
```

`llmbroker env` печатает заготовку с подсказкой над каждым ключом — где его
получить. Заполните те, которые легко достать: модель без ключа просто остаётся
неактивной, это не ошибка. Брокер сам читает `.env`, лежащий рядом с
`llms.toml`; переменная окружения важнее его.

`llms.toml` — обычный TOML-список моделей; его можно редактировать и дополнять
своими endpoint'ами. Провайдеру, не терпящему параллельных запросов с одним
ключом, укажите `parallel = 1` в его записи.

!!! tip "Ключи не обязаны лежать в `.env`"
    AWS Secrets Manager, Vault, БД или своё хранилище — см. [API-ключи](secrets.md).

### Держать пул свежим {#sync}

Провайдеры приходят и уходят, курируемый пресет за ними следует. Обновление
своего файла — одна команда:

```bash
llmbroker preset freetier --sync llms.toml
```

Она переписывает модели пресета и подсказки к их ключам, сохраняет ваши
`[[custom]]`-записи и печатает отчёт о сделанном. Из кода та же операция —
`llms.sync("freetier")`, и она возвращает этот отчёт:

```python
report = llms.sync("freetier")       # имя пресета — единственный вызов в сеть
print(report)                        # или отправьте в свой админский канал
```

Но обычно это не нужно. **Курируемый список поддерживает себя сам** — без
аргумента и без задачи в расписании: провайдеры закрывают бесплатные endpoint'ы
без предупреждения, поэтому список, который перестал обновляться, постепенно
перестаёт работать. Брокер перепроверяет его примерно раз в сутки, лениво — на
вызове, который вы и так делали, никогда по таймеру, так что простаивающий
процесс не делает ничего.

Обновление best-effort: если каталог недоступен, брокер напишет предупреждение в
лог и продолжит на том конфиге, который уже есть. Явный вызов `llms.sync(...)`
наоборот бросает исключение — вы его запросили, вам и обрабатывать.

**Проверка, которая ничего не изменила, ничего и не трогает.** Ваш `llms.toml`
переписывается, только если курируемый список действительно сдвинулся, — файл под
контролем версий остаётся побайтово тем же, вместе с mtime.

Чтобы следовать своему списку вместо нашего — назовите его; чтобы не следовать
ничему — скажите об этом:

```python
llmbroker.Broker("llms.toml", sync="my-lineup.toml")   # ваш, поддерживается свежим
llmbroker.Broker("llms.toml", sync=None)               # ничего не обновляется
llmbroker.Broker("llms.toml", sync_interval=3600)      # проверять раз в час
```

### Где llmbroker хранит своё состояние

Кроме вашего конфига llmbroker кэширует немного своего: скачанный пресет, платный
каталог и время последней проверки обновлений. Всё это лежит в одном каталоге на
машине — `~/Library/Caches/llmbroker` на macOS, `$XDG_CACHE_HOME/llmbroker` на
Linux, `%LOCALAPPDATA%\llmbroker` на Windows. Перенести его можно через
`$LLMBROKER_HOME` или для отдельного брокера через `home=` — так два проекта на
одной машине держат полностью раздельное состояние. Ничто там не является
источником истины: удалите каталог или запуститесь там, где писать некуда, —
брокер продолжит работать, просто скачает заново.

Конфиг `.toml` синхронизируется только из курируемого пресета. Чтобы раскатать
завендоренный конфиг в реестр в базе, см. [Серверы и кластеры](server.md).

В отчёте стоит понимать четыре вещи:

- **Ожидающий ключ (pending key)** — модель ждёт ключ, который вы не задали. Это
  безобидно: она остаётся неактивной, а пул работает на остальных. В отчёте
  написано, где взять ключ.
- **Оставленная запись (kept)** — модель, чей провайдер ушёл из курируемого
  списка, пока у вас ещё есть ключ к нему. С ней ничего не происходит: она
  маршрутизируется ровно как раньше и исчезнет сама, когда перестанет работать.

  ```
  kept: openrouter-nemotron — the lineup no longer carries OPENROUTER_API_KEY
  and this installation has a key for it, so it stays
  ```
- **Списанная запись (retired)** — та же модель после того, как ваш собственный
  журнал вызовов доказал, что она мертва: хотя бы один 401/403/404 и ни одного
  успеха. Неделя из 429 и 5xx не доказывает ничего и ничего не меняет. Удаление
  записи из вашего конфига — единственное разрушительное действие синхронизации,
  поэтому строка показывает доказательство:

  ```
  retired: groq-llama-3.3-70b — 401 since 2026-07-02, no successful call since;
  the lineup dropped it too
  ```
- **Неиспользуемый ключ (unused key)** — ключ, который у вас реально есть и на
  который в вашем конфиге больше никто не ссылается. Отзывать ли его у
  провайдера — ваше решение, а `[[custom]]`-запись, которая его ещё использует,
  убирает этот совет вовсе. Провайдер, ключа к которому у вас никогда не было,
  просто тихо исчезает — отзывать нечего.

Всё правило в одном: синхронизация никогда не отбирает модель, которую вы можете
вызвать, — разве что её заменяет тот же провайдер или ваш журнал говорит, что она
не работает.

### Наблюдение за пулом {#pool-health}

Один вызов отвечает на вопрос «здоров ли пул?» — факты по моделям и картина по
пулу целиком приходят с одного объекта:

```python
snap = llms.snapshot()

print(f"{snap.providers_usable} of {snap.providers_total} providers usable")
if snap.degraded:
    print("остался один лимит — переключаться некуда")

for key in snap.missing_keys:
    print(f"{key.api_key_ref} держит {', '.join(key.entry_names)}")
    print(key.help)                      # где его взять

for name, llm in snap.items():           # по-прежнему отображение имя -> факты о модели
    print(name, llm.has_key, llm.cooldown_until)
```

Единица счёта — провайдер, а не модель: две записи на одном API-ключе — это один
лимит, и считаются они один раз. Пул с одним работающим провайдером —
**degraded**: отвечать он ещё может, но при rate limit переливаться некуда.
Отзовите или смените ключ — счётчик догонит на ближайшем reconcile, так что числа
не отстают от ваших ключей. Модели, выключенные вами вручную, продолжают считать
своего провайдера: этот вердикт виден в строках моделей выше.

Тот же вердикт llmbroker пишет в лог, так что на него можно повесить алерт без
опроса. Обе строки — `ERROR`, и вы получаете по одной на каждую смену состояния,
включая падение с первой во вторую:

```
pool degraded, no failover left: 1 of 3 providers usable — no key for GEMINI_API_KEY, GROQ_API_KEY
pool cannot serve any request: no provider has a key — no key for ...
```

Восстановление пишет один `INFO` (`pool recovered: 3 of 3 providers usable`);
появление следующего провайдера после этого отдельной строки не стоит. Сами по
себе недостающие ключи никогда не алерт — двух провайдеров может быть ровно
столько, сколько вам нужно.

## Вызов брокера {#calling}

```python
llms = llmbroker.Broker("llms.toml")

reply = llms.ask("Переведи на английский: Привет мир")
print(reply.text)

# Полный messages API
reply = llms.chat([
    {"role": "system", "content": "Отвечай кратко."},
    {"role": "user",   "content": "Что такое Python?"},
])
```

Ограничить время всего вызова:

```python
try:
    reply = llms.ask("Вопрос", wait=5.0)   # максимум 5 секунд от начала до конца
except llmbroker.NoLLMAvailableError:
    print("Никто не ответил за отведённое время")
```

`wait` покрывает обе половины вызова: ожидание свободной модели *и* сам ответ.
Провайдера, который к концу бюджета всё ещё думает, брокер бросает — и не
наказывает за это, потому что дедлайн был ваш, а не его вина. Без `wait` одна
попытка ограничена только внутренним потолком в 60 секунд.

При этом модель, не уложившаяся в ваш бюджет, перестаёт быть первым выбором для
столь же коротких бюджетов — следующий вызывающий получит соседа, а не ту же
ловушку: за находку платит один вызов, а не все. Ничего не отключается:
вызывающие с более щедрым бюджетом по-прежнему идут к этой модели первыми, она
используется, когда других не осталось, а первый её удачный ответ метку снимает.

`wait=0` — единственное исключение: это «не вставать в очередь», а не «ответить
мгновенно»: пробуются все модели, свободные прямо сейчас, но своего дедлайна на
ответ вы не задаёте. Закрывать брокер в скриптах не нужно; когда всё же нужно —
см. [Серверы и кластеры](server.md#closing).

Чтобы печатать ответ по мере написания, а не целиком, пул умеет стримить —
`async for delta in llms.stream(...)`, только async, см.
[Асинхронность](async.md).

## Оценка качества {#quality}

Оценивайте ответы — брокер выучит, какие модели хороши для каких задач:

```python
reply = llms.ask("Кратко перескажи этот пункт договора", operation="summarize")
reply.record_quality(0.9)   # 1.0 — хороший ответ, 0.0 — неудачный; вне [0, 1] — ValueError
```

Оценки копятся по паре `(модель, операция)`: модель, стабильно слабая на данной
операции, уходит в конец очереди. Демоция мягкая — если других моделей нет, она
всё равно ответит — и снимается новыми хорошими оценками; отдельного «сброса»
нет. Вызовы без `operation=` попадают в один общий bucket.

**Оценить позже.** Вердикт часто приходит спустя долгое время после вызова —
пользователь просматривает созданный LLM артефакт через день. Сохраните
`reply.llm_name` и переданную операцию во время вызова, а оценку запишите, когда
она появится:

```python
# во время вызова сохраняем нужное
llm_name, operation = reply.llm_name, reply.operation

# ...через день, когда приходит отзыв пользователя
llms.record_quality(llm_name, operation, 0.0)
```

Это попадает в тот же bucket `(модель, операция)`, что и `reply.record_quality`;
исходный вызов может уже не существовать — оценка самодостаточна.

Пороги и размер окна оценок настраиваются — см.
[`Optimizer`](reference.md#llmbroker.Optimizer).
